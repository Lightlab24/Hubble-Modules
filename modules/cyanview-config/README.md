# Cyanview configuration module

Version 0.1.50 · module ID `lightlab-cyanview-config` · workspace host module for Hubble 2.0.18 or later with the spreadsheet controls, column groups, layout, and extended editing features.

Cyanview owns the two tabs, camera and network layouts, and device workflows. The Camera Configuration sheets use Hubble's Patch Sheet spreadsheet controls for selection, clipboard, series fill and the Button Matrix choice editor. Cyanview's amber cell tint and corner marker follow staged edits until device readback verifies them.

## Included

- Devices: one sheet with a row per managed RCP, RIO and Gateway: Name, Type, Serial, Status, Base IP, the LAN IP settings (a LAN IP column for every address a device has, and one to spare) and WAN settings (Mode, WAN IP, Gateway, DNS 1, DNS 2) groups that fold away, Connected on, Cameras and Sync. Click a heading to sort. Address changes wait in Pending sends until Send; the protected management (Base) address can't be changed. A device is added by typing or pasting its IP in the last row. The bin beside a name clears only its managed entry and local camera/LAN drafts, with session Undo; it never removes hardware configuration. The sheet is the only view: the Details view, a card per device, was removed in 0.1.91 (Nov 20, 2026) as a repeat of the sheet. Two things only the cards did went with it: typing the connection IP by hand and choosing a LAN address's interface.
- **A camera needs no address** (0.1.109). A camera with an empty Camera IP can be added and sent, so a virtual camera, or one whose address isn't known yet, doesn't wait on one. Only an address that isn't one is refused (`Invalid IP`). On **Defaults**, typing `None` in a model's Camera IP or Username gives that model's new cameras none.
- **Every LAN address is listed** (0.1.108). Folded away, the LAN IP column shows a device's first address and how many more it has (`+2 more`), which opens the group; open, there is a column for each. Typing over a LAN IP changes that address on the device, in place. Emptying one removes it from the device once sent: its cell keeps the address, struck through, and Pending sends reads `→ Removed`. A blank address entry on a device, one with no interface and no address, which a controller reports as a WAN, is listed after the addresses as **Blank entry** with a remove button, and is never taken for the device's WAN. An address already on another Cyanview controller, or on the same device, is refused before anything is written.
- Finding devices is one line in the Devices toolbar. Fast IP discovery pings in parallel with four-byte payloads, checks port 80 on responders and reads the Cyanview identity before displaying a result. Known/neighbor addresses are also verified immediately, including devices that block ICMP. Choose `10.192.0.0/16`, `10.20.0.0/16` or a custom `/16`–`/32` filter. Broadcast discovery remains available. Found RCPs, RIOs and Gateways list as rows under the managed ones, each with Add, and Add all; nothing is added without one of them. Device identity deduplicates aliases. Found rows stay through scan updates and Refresh all.
- A device's own web page is one click from its address on the Devices sheet. Base IP is the link, and an address that can be typed over (LAN IP, LAN IP 2, WAN IP) shows a small button beside it when the pointer or the keyboard is in the cell, which opens the address the device has now. The page opens in Safari on the computer Hubble runs on, or in that computer's own browser where there is no Safari. A module page can't open a window itself, because Hubble shows it in a frame that opens none, so the module's helper starts the browser with `http://` and the checked IPv4 address and nothing else. Someone using the dashboard from another computer gets the page on the Hubble computer, not their own. The helper takes up to eight requests at once, so a link still opens while a Discover search has a ping batch going on each of its four workers. At four, it said "Helper request capacity reached" until the search finished (fixed in 0.1.93).
- Saved devices: every RCP, RIO and Gateway added to the list is saved with the workspace, by serial with its addresses, and stays saved after it is removed. No name is kept, because a device is named for the job it is on. Discover checks saved devices that aren't in the list before the sweep, at every address each was known by and whatever range is chosen, and lists the ones that answer first on the sheet, Found with Add, under the name the device reports now. Since 0.1.103 one that is still being checked or didn't answer isn't on the sheet: it stays in Saved devices, which says Checking…, Didn't answer or Found beside each. Forget takes a device off the saved list only; a device in the list can't be forgotten.
- Camera logins (on the **Defaults** tab since 0.1.105): a Username and Password per camera model, saved with the workspace. They fill a camera's Username and Password when it is added or its model changes, however the model is set (list, typing, paste or fill). Cameras already set up keep theirs, and anything typed afterwards wins.
- **Defaults** (0.1.105) is a tab for what a new device or camera is called and where it is. Names and addresses are patterns with wildcards between % signs, typed or put in at the cursor with the **+** buttons: `%number%` is the device's or camera's number and `%type%` a camera's type. In an address, `%number%` and the digits next to it make three digits: `10.20.101.1%number%` gives RIO 5 the address 10.20.101.105 and RIO 21 10.20.101.121, and `10.20.101.%number%` gives RIO 21 10.20.101.21; leading zeros are dropped from what is sent. A number that doesn't fit gets no address and says why, and a pattern that can't make an address is marked under its table. **Devices** has a name, LAN IP and mask for RCPs, RIOs and Gateways. **Cameras** has a camera name (`%type% %number%` to start), a camera IP, a username, a tick for "A camera added to a RIO takes the RIO's number", and a row per camera model with its `%type%` (the model name when blank), its own camera IP if it needs one, and its username and password (the old Camera logins). A new workspace starts with RCP `RCP %number%` at `10.20.101.2%number%`, RIO `Cam %number%` at `10.20.101.1%number%`, Gateway `Gateway %number%` with no LAN IP, and cameras at `10.20.100.1%number%`. Defaults are saved and exported with the workspace (`plan.defaults`; each model's type and IP ride in `plan.cameraLogins`, which an older version reads and drops). RCPs, RIOs and Gateways are numbered separately on the Devices sheet, each in its own section, so there can be an RCP 1 and a RIO 1, and numbers can have gaps. The # cell is the device's number: typing one renumbers it (a number its kind already has is refused), and typing a name that fits its pattern, such as "Cam 20", renumbers it too. A device added by hand (Discover, Saved devices, the New device row) takes the next number of its kind, the name it makes and its LAN IP, which waits in Pending sends; in Setup mode that comes after the RCP is cleared. A controller the rig search finds keeps its own. A workspace saved before numbers takes each device's number from its name when it can ("Cam 12" is RIO 12, "Cam 6 Tally" RIO 6). A new camera takes its name, address and login from Defaults; on a RIO it takes the RIO's number, as it does when a RIO is picked as its Source, unless its number was typed. A name or address that still matches its pattern follows a new number or model; one typed by hand is never replaced.
- Camera Configuration: one expandable sheet per controller, mixed RCP/RIO ordering with drag handles, Expand/Collapse all, per-controller Add camera dropdown, camera IP/port/username/plain-text password and lens settings on the same row.
- REMI cameras: choose a managed source in the receiving controller’s Add camera menu, then add one, selected, or all cameras. The module reuses or creates the receiver’s manual IP connection. REMI settings offers an address override and tag editing. Device names are workspace labels used throughout the module.
- **Camera Configuration** is one list of every camera with all of its settings, and a bin on every row. **Add camera** needs no controller. A new camera reads "Not assigned" and stays out of the worker until it has a Source. Picking a **Source** and pressing Send creates it on that device. Changing the Source of a camera already on a controller moves it there: it is created with its settings, its copies come off, it is deleted from the old controller and its copies are rebuilt, so it drops off those RCPs briefly. A lens connection only comes along if the new controller offers the same port. **REMI Matrix** is where a camera is attached to other RCPs: its Source read from Camera Configuration, a **Master RCP** dropdown, and a circle per RCP or Gateway. A filled circle sends the camera on to that RCP. Its copies go from the source to the master, then from the master to each filled circle, and with no master straight from the source. A **Matrix / By controller** switch opens the sheets of each controller. **Pending sends**, on all of these, lists what is waiting, with Send and Cancel per camera, Cancel per change, Send all and Cancel all. Since 0.1.103 every camera row has two buttons, an eye and a bin, and right-click offers both. Since 0.1.104 their hover text, and Clear workspace's, shows after about a tenth of a second, drawn by the page; the browser's own title text took more than a second. The **eye** (Clear from workspace) takes the camera, and the REMI copies made from it, out of the workspace at once and sends nothing, so it works with every controller off; nothing waits in Pending sends and ⌘Z puts it back while the page is open. **Clear workspace**, on Camera Configuration's toolbar, does that to every camera. Hubble remembers where each cleared camera was, so when a read finds it on its controller again, Refresh all or the read that follows any send, it is listed under **Not set up by Hubble** instead of coming back. The **bin** (Clear from RCP) opens a check that names the camera and the REMI copies that come off first, then deletes it on its controller at once, whatever the Send mode. A controller that reads Offline can't be cleared, and the check says so and points to the eye. A camera that never reached a controller just goes. The REMI Matrix's and each controller sheet's Delete camera button, and lowering the camera count, still only mark a camera, which is struck through until it is sent, and its bin then keeps it. Clear from view, an eye that hid a camera for good, was removed in 0.1.94 at the user's request; the 0.1.103 eye is different because a camera it clears comes back under Not set up by Hubble when it is found. Auto send still sends circles at once, while a delete, a move and a change of master always wait for Send. A camera that can't be reached or moved stays in the list and says why, and the others still go. A camera can be moved or deleted while the controller it is on is off, which is often why it is moving (0.1.92, Nov 20, 2026). The move is done everywhere else: the camera is created on its new Source with its settings, its old copies come off the RCPs that hold them, and it is REMI'd again with the same master and circles. Taking a circle off works the same way. The camera left on the controller that is off leaves the sheets, and **Delete camera** for it waits in Pending sends until that controller is back online, then goes when it is sent. Cancel puts it back in the sheets. Refresh all keeps it waiting. Every other controller a move or delete involves still has to be on.
- Changing a source camera's name, number or model refreshes its REMI copies, including a chain through a master RCP. Any other edit, such as an address, login or lens, leaves the copies and their controllers alone. The module saves the chain, removes downstream copies first, and restores them from the source outward. Retry REMI refresh resumes saved progress after a failed hop. Imported rows show the original camera model and source controller’s workspace name when known. Remove those rows through REMI. A copy whose source is off or out of the workspace, so that nothing imports it any more, still comes off: **Remove REMI copy** deletes it from the controller it is on.
- Iris, Zoom and Focus settings are off by default on each camera. Expand a lens section and tick **Use Iris**, **Use Zoom** or **Use Focus** on the camera row to set that axis up for Tilta Nucleus-M or direct ARRI cforce. Its settings start blank until you enter them or the controller reports them, and an axis is sent once all of them are filled in. New sheets start with header-only collapsed lens sections; existing saved collapsed fields keep their visibility. A dash means the axis is unavailable for that lens. Use **+** in the group header to reveal its fields at their own widths. Right-click the header and open **Collapsed fields** to choose which fields stay visible. Delete turns a Use box off and clears any other cell. Turning a box off drops its pending edits and leaves the controller alone. Sending a deleted setting clears it from the controller. The controller keeps each axis as one entry and can't hold part of one, so the whole axis comes off and its other cells empty. A Tilta iris with its limits deleted is the exception and keeps its motor. Deleting Lens connection sets it to None and sending disconnects it. Setting the lens model to None clears all of its axes. Camera number, name, model and IP are required, so deleting one marks the row Incomplete until it's filled in.
- Camera, Lens and Sync header bands organize the camera sheet. The strip above each sheet shows the active camera and field, with keyboard hints and the Columns menu. Real camera numbers remain editable. Passwords show as typed, in the strip too.
- The shared Columns popup searches section and field labels. Toggle Camera, Lens, Iris, Zoom or Focus independently without losing field choices. Drag across field checkmarks to preview a range, then release for one save and one Undo step; Escape cancels. Selected **Collapsed fields** remain visible.
- Each camera sheet has shared text-size controls (9–24) saved with its layout. Pinch or Ctrl-wheel zooms the whole sheet independently; zoom resets when the page reloads. Undo/Redo covers layout changes and staged camera setting edit batches, including paste and fill. It does not replay camera commands or undo settings already verified on hardware.
- Drag a column edge to resize it or drag the bottom edge of the row gutter to resize the row. Each controller's sizes, collapsed fields, and expansion state save with the workspace.
- Right-click a camera row and choose **Delete camera**, or select a cell and click the card's **Delete camera** button. The button names the active camera, including when a range spans several rows. The confirmation shows the camera and its controller. Imported cameras use REMI removal.
- Camera sheets default to ascending numeric camera number. Click any data column header to sort; click again to reverse it. Each controller retains its own selected column and direction. Sorting changes the view without renumbering cameras or sending configuration.
- Manual send by default. Auto send applies valid committed edits on Enter, Tab or blur, without sending intermediate typing or previously staged edits when enabled. Reconnecting does not replay pending writes.
- Sending submits all selected pending rows together, with a separate verified result for each row. Controllers work side by side. On one controller, edited and deleted cameras go together over one connection and are confirmed from what the controller reports back; a new camera, a changed camera number and a network change each take their turn. The saved configuration is written once per send, and not at all when nothing on a saved row changed.
- A rig that was set up outside the module is read in as it is. Every controller lists the others it has seen, so after **Refresh all**, or after a controller is added, each listed serial is tried at its base address and the ones that answer are added to Devices under their serial numbers, with their cameras, settings and the REMI copies they hold. Nothing is sent to a controller for this. A controller removed from Devices is left out of that search until it is added back by hand. The search doesn't run while Setup mode is on (0.1.108).
- A controller's **base address** is the one in its serial: `CY-RCP-46-197` is always 10.192.46.197, and the controller marks that row, and only that row, ReadOnly. Since 0.1.102 that decides it. A WAN or a LAN address set inside 10.192 is never taken for the base, whatever order the controller lists its rows in, and a WAN inside 10.192 shows amber in the WAN column. A LAN address inside 10.192 can be replaced like any other.
- **Setup mode** (0.1.102), beside Send mode, clears RCPs so they can be set up again. While it is on, every RCP added to Devices (Discover, Saved devices or the New device row) is cleared as soon as Hubble reaches it: every LAN address deleted, however many it has, the WAN left Static with no address, gateway or DNS, and every camera deleted the way **Clear all** deletes them. The band's ticks choose which of the three happen. **Clear the RCPs already here…** opens a review listing each RCP and exactly what it loses, and any can be unticked. RIOs, Gateways and each RCP's base address are never touched. Since 0.1.108 nothing joins the list by itself while Setup mode is on: the search for the rest of a rig used to add the other RCPs right after the first one, and those were never cleared. The addresses are cleared whatever became of the cameras, a blank address entry goes with the LAN addresses, and a clear that could only do part says which part. Everything goes over the base address, so an RCP that doesn't answer there is left as it is and its Sync reads Not cleared with the reason. Setup mode starts off each time the page opens and is never saved in the workspace, so an opened or imported workspace can't clear anything by itself.
- A camera or REMI copy that a read turns up, and that wasn't in the list before, was set up outside the module. Since 0.1.103 so is every camera already on a controller you add to Devices yourself, by Discover, Saved devices or typing its address; before that, only a controller the rig search added had its cameras listed apart. The Simulated rig is the exception: it stands in for a rig already set up, and its setup tour counts those cameras as yours. Since 0.1.94 it isn't mixed into your cameras: Camera Configuration lists it under **Not set up by Hubble**, below your cameras, and it isn't counted in your cameras, the REMI Matrix or the sheets of each controller. Each row has **Move**, which makes it one of your cameras and sends nothing, and **Clear**, which marks it to be deleted from its controller along with any REMI copies of it. A cleared camera waits in Pending sends like every other delete, and Keep takes it back. **Move all to my cameras** and **Clear all** do every row. A camera and the copies of it that arrived with it are one row; a copy someone made by hand of one of your cameras is its own row, and Clear takes off only that copy. A camera of yours that a controller deletes and adds back under a new key, with the same number, is still yours. What the module sends itself is never listed there, and neither is anything already in the list when this was introduced. The rows can't be edited until they are moved in.
- A send only opens the controllers it changes. A camera edit opens that camera's controller. Adding a REMI copy opens the controller getting it and the one it comes from, and taking one off opens only the controller it is on. Copies are found from what the module recorded and last read, so a copy made by hand on a controller is picked up by the next **Refresh all**. Each send's duration is written to Hubble's log as `module_send_timing` or `module_route_timing`. Further sends to the same row wait for its current send; network replacements retain their connection and identity verification sequence.
- Auto sends and confirmed deletions on different cameras also run concurrently. Deleting a camera waits for its active edit, then blocks further edits to that camera. Concurrent draft saves preserve generated IDs and cannot restore deleted rows.
- Cached camera or controller Offline status never blocks sending. Each send attempts a fresh connection; connection or verification failures leave the edit pending with an error.
- Status sockets retain the documented text keepalive and use WebSocket protocol ping/pong to verify liveness, including controllers that do not reply to text pings.
- Type to replace a text cell, or double-click, press Enter or press F2 to edit its current value. Enter, Tab and blur commit the edit. Escape cancels it. Choice cells use the Button Matrix popup with a checked current value, grouped options, and live controller choices. Type in a selected choice cell to search.
- Saved dropdown choices are available after reload and when a controller is offline. Adding or refreshing a controller saves its camera models. Open other choice lists while connected to save the controller-specific lens and connection options. Offline edits can be staged and sent after reconnection.
- Drag across cells or Shift-select a range, then copy or paste with the standard keyboard shortcuts. Paste rectangular tab-separated data into existing camera rows. Read-only and inactive fields are skipped.
- Drag the selection’s bottom-right handle to fill. Camera numbers, names and IP addresses continue a consistent series. Other fields repeat their values.
- Workspace storage for plans, credentials, ordering, expansion and hidden columns. Up to 128 controllers and 512 camera rows.

A LAN address change rewrites the address the controller already has, in place: only what differs is written (mask, then address), followed by the save, and what the controller reports back on the same socket confirms it. Nothing is created and nothing is deleted, so a controller never ends up holding the old address and the new one. Until 0.1.108 a change created the new address, looked for the controller at it and only then deleted the old one; when that look reached another controller or nothing (Nov 23, 2026), both addresses stayed and the sheet listed one. Address changes go over the controller's base address when it answers there, and a controller reached only by the address being changed is found again at the new one. A new address is the only thing that creates an element; one that can't be finished is deleted again, and its ID is stored at once so an interrupted add isn't repeated. An uncertain create requires reconciliation with Refresh before further action. Changing an existing LAN address in place has been run on simulated controllers only; the write is the one that sets a new address's IP and a WAN's Static address on real ones.

## Setup tour

**Setup tour** in the page header walks through this page in the order Cyanview is set up. Each stop dims the page around one part, rings it, and points at it with a short arrow and its name. A panel fixed at the bottom of the page says what that part is for and, where there is something to do, what to do there. **Exit tour**, **Back** and **Next** sit on the panel's bottom edge, in the same place on every stop, so the mouse never has to follow them. Next moves on whether or not the stop was done, and Esc leaves; → and ← move between stops while the panel has focus. The tour opens each stop's tab itself, and the page stays usable under it: the ringed control can be used without leaving the tour.

The 24 stops follow seven steps:

- **Find your controllers:** Discover (the network list, discovery method and Discover, with Saved devices and the New device row in its text).
- **Name your controllers:** Name, Status and Base IP, LAN and WAN.
- **Add your cameras:** a stop of its own for the move to Camera Configuration (still on Devices, with the Camera Configuration tab rung), then Number of cameras, the camera details from name to password, Source, and Camera Control Enabled, the ticks the group actions act on. A sheet that hides that column has Columns rung instead, with a word on turning it back on.
- **Send to the controllers:** Pending sends, Send mode.
- **Share cameras with REMI:** the move to REMI Matrix, then Master RCP and REMI to, which is optional.
- **Add Cyanview actions:** the actions are set up in HubDash's Button Matrix, which this page can't show, so these stops draw an example of it in the Button Matrix's own look, with this setup's controller names and camera numbers, and ring its parts: **+ Action**, the **Action** column with its list open under its two headings, then **Cyanview Controller** and **Camera**. Six more stops go through every Action, group by group (one camera, the ticks, Recording, ND, ISO and Base Gain, White Balance and presets), each with example rows and a line on what each Action does.
- **Press a key.**

Headings are found by the column they name (`data-device-header`, `data-device-group-header` and `data-field-header`), never by their words, so a sort arrow or an open group never loses them. A sheet column is rung whole, heading to last row; the tour scrolls it clear of the panel when it fits, scrolls past frozen columns, and puts every scroll back when it ends. While the tour is on, each tab ends with room for the panel, so no row stays hidden under it.

Each stop shows its step, with a green tick once the page or the worker can see the step done: controllers in Devices, controllers no longer named by their serial number, cameras with a Source (counted as Camera Configuration counts them, so a REMI copy is not another camera), nothing waiting in Pending sends, REMI copies, Button Matrix keys with a Cyanview action, and a press. A step's first stop says where it stands, such as "You have 3 controllers. 3 are online." The ring, arrow and tag keep still for reduced motion, and the tour follows light and dark mode.

The tour starts by itself the first time the page loads with no controllers, and never again after that. That, and a press once seen, belong to this Mac, not the workspace, so they are kept in the module's runtime folder (`setup-guide.json`) and never exported. A module page's frame has no storage of its own, which is why the worker keeps it. A simulated setup is walked through apart from the real one. With Simulated on, the header says so, and the Discover stop says what Discover finds.

To see the page at a real setup's size, the preview's `/__load` route restarts its worker on a copy of a workspace's Cyanview documents (`{ documents: [{ id, value }] }`). Every connection still reaches only the preview's loopback simulator.

## Cyanview controls and RCP routing

Add a **Cyanview** action column in Button Matrix. Choose the Action and the named **Cyanview Controller**; camera-specific actions also take a camera number, with a filtered list of camera names and support for formulas and series fill. The Action dropdown has separate **RCP set active camera** and **Cyanview** headings. **Select camera** is under the RCP heading; recording, group selection and exposure actions are under Cyanview. Existing saved action values stay valid. Controller choices list every managed RCP, RIO and Gateway, store stable identities and display the workspace name plus serial, or the serial alone while the name is still the serial. **Select camera** lists RCPs and Gateways. Renaming or changing a controller address preserves button assignments. New rows start with no Action. A row with no Action is simply empty: nothing on it is flagged as missing, its other cells are inactive until an Action is chosen, and it sends nothing. Any Action needs a controller, and camera-specific Actions also need a camera number. A row that already has **Select camera** saved from an earlier version keeps it until it's changed or cleared.

Each existing Camera Configuration row has **Camera Control Enabled**, including REMI rows. These checkmarks define the quick group on that controller. They save immediately as local workspace selection, independently of staged device settings and Manual/Auto send. Existing and new cameras start unchecked. Checkbox edits support shared spreadsheet paste and fill.

Each controller card in Camera Configuration has **Single switch** and **Enable all** controls, and shows how many of its cameras are enabled and how many of those are unavailable. These controls act at once and don't wait for the save. If a save fails, the edit and any later edits on that controller roll back, a message appears, and other work is kept.

Each camera row also has read-only **Recording** and **Status** columns. **Status** shows what stops the next press first (for example `Recording locked`, `Camera offline` or `Waiting for fresh camera state`), otherwise the last press's result, otherwise `Ready`. Every managed RCP, RIO and Gateway keeps one connection to its MQTT broker from when the worker starts, whether or not a camera is ticked, so they fill in by themselves. That connection only subscribes, sends no commands and reconnects by itself. Until a controller has answered, both columns stay empty rather than guess. They can be hidden with **Columns**.

**Control** and each controller's mark read **Online**, **Offline** or **Not checked**. They come only from that MQTT connection, the same state **Status** reads, so the two can't disagree. Offline follows a connection that failed, a camera that reported it, or a camera the controller lists with no connection report. The RCP keeps a report for every camera whose RIO is up and drops it when the RIO goes, so a listed camera with none has no RIO reaching it; **Status** then reads `RIO offline`. Not checked means nothing has answered yet.

Camera keys (Select camera, Record camera, Enable/Disable camera) show the camera's connection path on the bar, one state at a time: **Online** (blue) when the camera reports online, **Camera offline** (yellow) when its RIO is reached with no camera on it, **RIO offline** (orange) when the controller can't reach its RIO, lists the camera with no report, or is down itself, and **Not configured** (grey) when no camera is set up behind the key: no controller has one under that number, the key names a controller the setup doesn't have, or a Select or Record camera key names none. A camera plugged into a Gateway or an RCP has no RIO, so where a RIO camera would read RIO offline it reads Camera offline. The RIO is a camera's only way in, so a Gateway or controller outage reads as RIO offline. A key with no controller named takes the furthest any controller gets. Recording rings the outline beside the bar. Each key can change these looks in Hubble. A Gateway runs its own broker as an RCP does, so it's watched and controlled the same way.

**Live settings.** The worker keeps one settings socket (`/ws/ui`) open on every managed RCP, RIO and Gateway, base address first, as it does for MQTT. A controller sends its whole configuration to every open socket after each change, whoever made it, so a change made in Cyanview's own page shows up in the sheets with nothing pressed. Only that controller is read, from the socket already open, and the merge keeps local edits, pending sends and a cell being typed in, as an MQTT camera change does. The socket only listens: nothing goes to the controller but the heartbeat its own page sends. A dropped socket is opened again, and a change made while it was closed is read when it comes back. Status still comes only from MQTT.

**One settings socket per controller.** A send, a Camera Enabled switch, a dropdown's list and REMI work all go down that held socket instead of opening another beside it. Opening one took about 120 ms on real controllers (Nov 10, 2026), and each extra open socket is one more the controller pushes its whole configuration to after every change. A held socket is only lent while its controller has answered the heartbeat within 7 seconds; otherwise the work opens its own socket, as it always did. While any work has a socket of its own on a controller, and for a second after, the held one isn't lent, because a controller reports a change to each socket separately and the held one could be a moment behind. Cancelling a request closes the socket it was on, and the worker opens the held one again within about a second. Refresh all, Find by IP, a single-row send and the check of a new LAN address still open their own. Because a read now waits its turn on that socket behind a send, a live read gives back what the controller has when it answers, and the page throws away any background read that was out while it asked a controller for a change, so a value just sent never flips back to the one it replaced. The look for a camera's REMI copies, which every Camera Enabled switch makes, reads the held sockets, leaves out at once a controller that answers on neither its settings socket nor MQTT, and gives one with no held socket 1.5 seconds to answer.

**Camera Enabled** is Cyanview's own Enabled setting on each camera, shown as On / Off beside Control. It isn't **Camera Control Enabled**, which is Hubble's own checkmark for the group buttons and sends nothing. A REMI copy stops being selectable on its RCP once the camera it comes from is switched off and on, until the copy is switched off and on itself. So switching a camera off takes every copy down the chain off, furthest first, and switching it on brings each copy back by switching it off and on in turn, nearest first, after its source reports online. This happens whether the switch is made here or in Cyanview's own page. A copy's switch is locked and says which controller it follows. The refresh button beside each switch, and **Refresh camera** on a camera's right-click menu, switch a camera off and on again and then do the same to its copies. On a copy, only it and the copies made from it are refreshed. Both send at once in either send mode, and the switch moves before the controller confirms and moves back if it refuses.

**Refresh all** reads every controller once over a fresh WebSocket, closes it, and merges changes made outside this module around local edits. It doesn't change any controller's status, and a controller it can't read is named in its message. Opening the page opens no connections.

Enable / Disable Camera, Enable / Disable All Cameras and Single switch only change the saved checkmarks, so they send nothing and need no connection. Their **Cyanview Controller** cell is optional. With a controller named they affect only that one. Left blank they cover every controller, and one press goes the same way on all of them: camera 3 is checked or cleared on every controller that has a camera 3. The other actions still need a controller. Single switch keeps one camera checked; Enable All exits Single switch. Record, ND, ISO, reported Base Gain and Sony VENICE Add preset commands affect only checked cameras on that controller. ND In, ND Out (Clear) and ND In / Out (Toggle) go only to checked cameras that report ND in/out, send what an RCP's own panel sends (`camhead/action/set/nd_filter_clear`, 0 for in, 1 for out), and wait for each camera to report the new state. The toggle takes the ND out when every such camera has it in, and puts it in otherwise. Their keys light ND in when every such camera has it in, and Some ND in when only some do. Base Gain Up and Down step every checked camera that reports a base gain, whether its own broker or an RCP or Gateway reports it, and leave out the others. On a two-base camera such as the Burano, Up is High and Down is Low. Their keys light High base or Low base when every such camera is there, and Mixed base when some are Low and some High. White Balance brings Hubble to the front with a dialog for a colour temperature (2000 to 15000 K) and, when a camera reports one, a tint (−99 green to +99 magenta), starting from the first camera's current values and listing every checked camera with what it reports now. While it is open, checking or clearing a camera, or a camera reporting a new value, updates the list and the Send button in place without touching what was typed. Send moves each checked camera that reports a colour temperature to the typed values the way an RCP's panel does (`camhead/action/add/wb_temp` and `wb_tint`), waits for each to report it, and leaves out cameras that don't; a camera with no tint gets the temperature only. Esc or Cancel sends nothing, and an unanswered dialog closes after two minutes. It needs a Hubble that can show and update module dialogs (module-prompt-v1 and module-prompt-update-v1). Select camera routes the RCP panel an RCP or Gateway reports, and says so if none has reported; Record camera targets one camera directly regardless of its checkmark. Record Group ALL has been removed for now. A row that already has it saved shows as invalid and sends nothing until its Action is changed or cleared. An empty quick group sends nothing.

Camera commands use the managed controller's MQTT broker on port 1883. A camera that isn't connected is sent nothing, on any command, and the press says so. The other cameras in the press still get theirs, and nothing is held to send later. A connected camera whose state is known is checked first and isn't sent what it's already doing. It gets the command it accepts, `Rec` or `Stop` for a switch camera and `RecToggle` for a toggle-only one. It then has 15 seconds to report its new state, plus half a second for each other camera in the press, up to a minute, so a press on many cameras doesn't read as failed while the RCP catches up. A connected camera that hasn't reported its state still gets `Rec` or `Stop` straight away, and the result says it wasn't confirmed. A toggle-only one waits for a report before Start or Stop, because a blind toggle could do the opposite of what was asked. A recording lock stops a recording command. Fresh configuration verifies the controller serial and applied camera numbers before sending, so a press still needs that WebSocket read to succeed. Send or refresh staged camera number changes first. Recording preserves per-camera ordering and bounded concurrency. Presses act in press order on each controller, and a tick made just before a press counts while one made just after doesn't. Exposure/preset delivery acknowledgment does not claim camera completion. No commands are retained or replayed after reconnect. Runtime recording uncertainty is local to the host and is excluded from workspace export; selection flags and per-controller Single switch state are portable module documents.

The new control runtime is packaged here, adapted from the RCP transport and CCC 1.2.9 recording implementation. It does not require the standalone RCP or CCC module. Existing standalone connections and buttons remain available alongside these new actions. All development device writes are tested with loopback simulators; physical camera operation requires a designated test target.

## Simulated

**Simulated** in the module's settings runs Cyanview controllers inside Hubble, so the whole module can be tried with no equipment. It is saved as `sampleData`, the id the old **Use sample devices** setting had, so a workspace that had that on opens in Simulated. Any made-up rows it saved then are still in its plan; they aren't the simulated controllers, so they never come online, and can be removed.

The simulated rig is a RIO, `CY-RIO-1-10` at 10.192.1.10 and 10.20.101.200, with two Venice cameras, 1 Wide and 2 Tight, and two RCPs, `CY-RCP-1-20` at 10.192.1.20 and 10.20.101.201 and `CY-RCP-1-30` at 10.192.1.30 and 10.20.101.202, that each have both cameras as REMI copies. Each controller answers on its settings socket and its MQTT broker the way a real one does, so everything works as it does live: Discover on any range or by broadcast, Find by IP, Find rig, adding the controllers, sends that are applied and confirmed, live settings, Refresh all, REMI, Camera Enabled and Refresh camera. Camera keys work against it too. Select camera switches the RCP's panel, Record camera, Start, Stop and Toggle Recording start and stop the camera, and the keys light Online, Camera offline, Selected and Recording as they would. A copy is the same camera, so a camera recording on one RCP shows recording on every RCP that has it. A camera that is switched off, or whose source is, reads offline, and so does a camera that has no model set yet. The simulated cameras don't report ND, ISO, white balance or base gain, so those keys say the camera hasn't reported one. A simulated controller has no web page, and its address says so instead of opening a browser.

Nothing goes on the network. Every connection to the simulated controllers stays inside the module's worker: no port is opened or listened on, no ping is sent, no broadcast is listened for, and no helper program runs.

Simulated keeps its own plan (`sample-plan`), REMI records, camera checkmarks, saved choice lists (`sample-choices`) and simulated controllers (`sample-rig`). The real ones are never read or written while it is on, so switching it off brings the real setup back as it was. Hubble shows the module as Simulated, and the page says Simulated beside its save status.

**What was sent survives a restart.** Each simulated controller's settings, its REMI copies, which cameras are recording and which camera each RCP has selected are kept in the `sample-rig` document. Hubble lets a module write its documents only during a command, so each page command and key press saves the rig on its way out when something changed, and a restarted worker puts the controllers back from it before anything connects. Anything that changes the simulated controllers between commands is saved by the next one. The rig isn't rebuilt from the saved plan instead, because the plan also holds edits that were never sent and doesn't hold what only a controller keeps, such as its REMI connections and which camera is recording. The simulated controllers travel with the workspace, like the rest of Simulated's documents.

## Build and check

Use Node 22.22.2 and pnpm 11.0.8 from the root of this repository:

```sh
pnpm install --frozen-lockfile
pnpm build
pnpm --filter @hubble-module/cyanview-config build
node scripts/modules.mjs test cyanview-config
pnpm --filter @hubble-module/cyanview-config test:ui
node scripts/modules.mjs package cyanview-config
```

`src/ui-controller.js` is generated from `src/approved-ui.js` and the `src/ui-*.js` partials by `tools/adapt-ui.mjs`. Run this module's `build` script after editing those files and commit the result, because repository-wide builds use the committed copy.

The package is written to `artifacts/lightlab-cyanview-config-0.1.50.hubble-module` at the repository root. Check for `module-spreadsheet-controls-v1`, `module-spreadsheet-column-groups-v1`, `module-spreadsheet-layout-v1`, `module-spreadsheet-extended-editing-v1`, `module-spreadsheet-column-editor-v1`, `module-spreadsheet-workbook-tools-v1`, `module-spreadsheet-column-visibility-v1`, `module-spreadsheet-column-paint-v1`, and `module-spreadsheet-text-size-v1` in the target host's `describe` response before importing. `Simulated` defaults to off; see [Simulated](#simulated).

The existing `studio` page uses Hubble's `full-page` layout with its single `frontend` section. The iframe fills the bounded host content area and owns its existing header, tabs and footer. Long content scrolls within the selected tab; no fixed section height is used. Hubble retains its sidebar and window controls. The sandbox, scoped SDK bridge, page disposal and generation invalidation remain intact.

Fast IP discovery uses the system `fping` utility, found in standard macOS/Linux installation locations; it is not bundled or silently installed. Four helper calls run concurrently, each covering up to 1,024 addresses at a one-millisecond interval, with no retries and a 300-millisecond timeout. Once 1,024 packets are waiting for ARP, macOS drops further first packets without telling fping, though it still sends the ARP request, so a sweep loses most pings to devices this Mac hasn't spoken to lately. The module therefore also reads the ARP table every five seconds during a sweep and once at the end, checks every in-range address that answered ARP, and gives an address whose first check failed one more once it shows there. This sends up to roughly 4,000 probes per second; the IP/ICMP headers add traffic beyond the four-byte payload. A full `/16` is not instantaneous, but verified devices appear as batches return. The Scan command remains open while the helper runs, so host cancellation and page closure settle its work. Stop cancels outstanding batches. If `fping` is unavailable, the module reports that explicitly; Find by IP and Broadcast discovery still work.

Broadcast discovery listens for Cyanview UDP/3838 announcements. If another app holds that port exclusively, the module reports it while continuing known-neighbor and manual IP checks. Fast IP discovery does not claim UDP/3838. Every candidate must return a Cyanview WebSocket configuration before it appears in the list.

`pnpm preview` serves the compiled UI at `http://127.0.0.1:43127`. It loads the shared spreadsheet runtime from `CYANVIEW_SPREADSHEET_HOST`, which defaults to the side host at `http://127.0.0.1:42841`. Set `CYANVIEW_RENDERER_ASSETS` to the qualified main renderer assets directory for offline checks without connecting to either installed host. The browser tests use the selected shared runtime, a module-owned SDK bridge fixture, and a loopback WebSocket simulator for every device connection. `POST /__reset` with `{ "simulated": true }` runs the worker in Simulated against its own simulated controllers instead; with `{ "sample": true }`, the default, the page shows its own made-up rows and sends nothing.

## Capture-dependent features

Camera model, endpoint, USB, lens model and lens connection commands resolve current options from each controller instead of reusing captured element IDs. Tilta Nucleus-M and direct ARRI cforce parameter editors use the documented formats only when the controller exposes a writable LensParams mapping; fresh readback confirms saved configuration. Unrecognized existing parameter formats remain blank and disabled to preserve their values.

REMI imports require the source controller to advertise the camera. Chained refresh and recovery are verified with simulated controllers. cGate configuration and calibration await separate captures. A WAN's DHCP or Static mode, address, mask, gateway and DNS are written with the commands a RIO WAN's own page sent (captured Nov 17, 2026): DHCP through the on or off command the controller offers, then the address and mask as separate writes. What a RIO shows for an address a DHCP server hands out hasn't been captured yet, so a DHCP send checks only the mode. Physical camera and lens operation require hardware verification.

The approved design hashes are recorded in `design-reference/ui-source-provenance.json`.

Browser fixture tests exercise resizing, long content, tab switching and sorting without physical hardware connections.
